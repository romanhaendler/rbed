# A stream resumes from a Snapshot, or from a Replay Point

An application that feeds a Detector from a message stream must be able to stop and continue as if it had never stopped: the same Events, at the same timestamps, with the same flags and Aggregates, each reported once. Replaying recent messages into a fresh Detector is only exact if the replay starts early enough, and the application cannot know how early. Three capabilities answer this together: the **Snapshot**, the **Replay Point** and the **Memory Horizon**.

## Snapshot and Replay Point, both

- **Snapshot: instant, exact, with a format to keep.** `detector.snapshot()` returns the complete state as a byte array; `Detector.builder()...restore(bytes).build()` continues from it without replaying anything. The price is a binary format that later versions must keep readable or reject deliberately.
- **Replay Point: no format, but a replay.** `detector.replayPoint()` tells the earliest timestamp from which a replay into a fresh Detector, with History of the Events Ended before it, reproduces the state. Nothing is stored but a timestamp and the Ended Events, so there is nothing to migrate. It is the fallback when no usable Snapshot exists (none taken yet, Rules changed, Snapshot lost or of an unsupported format version), and it bounds the replay of the messages after the latest Snapshot.
- **Memory Horizon: a configuration bound.** It tells how far back the configuration looks (longest window, largest Sample count) so operators can size retention and the Snapshot interval. It is not a guarantee: an Event in progress can reach further back, which only the Replay Point accounts for.

## The guarantee

A Detector restored from a Snapshot is observationally indistinguishable from the one the Snapshot was taken from: for every input that follows, every callback (kind, order, the complete Event, every Aggregate bit for bit), `value(...)`, `retainedValues()`, `droppedValues()`, the warnings logged and every exception (type and message) are identical. There are no preconditions beyond those `build()` enforces. Any difference is a bug. This is why state is written as raw bits (NaN, -0.0 and the accumulator words of moving averages included) and why the tests compare twins at every moment.

## The format

All written with the JDK only:

1. the magic bytes `RBED` and the **format version** (an int, currently 1);
2. a **fingerprint**: a 128-bit hash (two 64-bit xor-multiply lanes over the UTF-8 bytes, each string preceded by its length: lane one is FNV-1a with its standard offset basis and prime, lane two the same construction with another offset basis and the multiplier 0x9E3779B97F4A7C15; hand-written because the compiled browser module has no `MessageDigest`; it guards against a mismatched configuration, not an adversary) over the Rules' canonical keys (`Key`, in the order added, plus the name and kind, Pulse or not, of every Channel) and, separately, over the watched Expressions' keys. A key is an injective encoding, not the readable `toString`: every name is length-prefixed (`3:abc`), every number delimited (`n5;`, doubles as their hex bits `d3ff0000000000000;`) and every construct a letters-only tag with its parts in parentheses (`above(channel(1:x)constant(d...;))`), so no name (dots, commas, quotes, parentheses, "pulse", digits) can make two configurations equal. The readable text is ambiguous (a Channel named `x.abs()` prints like `x.abs()` on Channel `x`; `unless(A, B)` like `unless("A, B")`) and is not used; then the sampling rate and the Retention Limit in plain. Separate parts let `build()` say which option differs;
3. the Detector's state: the latest moment and the Sample index, the closed flag, the retained and dropped counters, History's latest end, every Channel's track (values, previous value, times, absence), every moving-average window with its exact sum (the non-zero limbs of the accumulator), and per Rule its state machine, its Aggregates, and the Event state other Rules read (counts, durations, confirmation times kept for `count(...).within(...)`);
4. a CRC-32 of everything before it, so a corrupted or truncated array is rejected rather than half read.

A window over a duration (a growing ring) is written oldest first, without its position or capacity. A window over Samples has a fixed capacity: its value and need arrays are written as they are, then its size, the position `next` of the slot written next, and the non-zero limbs of the exact sum. Either way a Snapshot of a restored Detector equals the Snapshot it was restored from byte for byte. The listener is not part of a Snapshot. The size is bounded by the Retention Limit, as the windows are.

`build()` throws `IllegalArgumentException` for an array that is not a Snapshot, is corrupted or truncated, has another format version, was taken with other Rules (also renamed) or other options, or is combined with `history(...)` (a Snapshot already contains what History would add). `snapshot()` throws `IllegalStateException` inside a listener callback, where a moment is half processed.

## The Replay Point

`replayPoint()` is an `OptionalLong`: empty before the first Sample and with a sampling rate (a fresh Detector cannot continue the Sample index; use a Snapshot there), otherwise a timestamp of a moment (Sample or time advance). Replaying every moment from it on (and `close()` if it was called) into a fresh Detector built with the same Rules and options and the History of every Event that Ended before it, then continuing, never differs from the original from the stop on. Reading it costs a loop over the Channels, moving averages and Rules, nothing proportional to history, and allocates only the result.

What it is made of (the spec's list was a start; the differential tests found the rest). Every recorded value needs only what it depends on, and the Replay Point is the minimum over all of them:

- **A Channel's value** needs its latest update, and the one before if `rate()`, `rising()` or `falling()` read it; `age()` needs the latest update even while a Pulse Channel is absent. **A moving average** needs the oldest entry of its window, and a duration window also the entry that proved it warm (the latest one that left by time). An entry needs what its value depends on: the Sample for a Channel, the source's window for an average of an average. Since the sums are exact (below), nothing else about the history matters, so a window lets go of everything that left it.
- **An Event in progress** needs the start of its run, and a **Rule still waiting for `when` to stop holding** after an Event that Ended on its End Condition needs the same: a fresh Rule would start another Event. The run starts where the decision to begin can be reproduced: the Event's start, lowered by what the Conditions read at that moment (the previous value behind `rate()`, the window of a moving average that the End Condition reads later, the Channels it aggregates, the latest Event of a Rule whose Aggregates it reads).
- **`when` seen false** (it decides `truncatedStart` of the next Event) needs the moment it was last seen false, lowered by what that evaluation read; an absent Pulse Channel read for its value reads nothing.
- **`latest(...)`** needs the start of the latest Ended Event of a Rule whose Aggregates are read, and not those of earlier Events. **`maxGap`** needs the previous Sample.
- **No run is split.** A replay may not start inside a run that is over (from where its start needs, to the moment it ended) if another Rule reads its Events or it ended on an End Condition: the Event would be neither History nor produced whole again, and an End Condition decides when it ends from values before the replay's start. The Detector keeps these closed runs as pairs until the Replay Point has passed them (merging neighbours if they fill the Retention Limit, which only makes the Replay Point earlier). A Rule that ends only when `when` stops holding and that nobody reads ends in the same state however its Event began, so it needs no such pair. Likewise, the time advances between two Samples are no start for a Detector with a `maxGap`: a replay would not notice the gap the Rules saw.
- Runs of different Rules that touch (a Rule starting in the moment another's Event ended) chain: the Replay Point stays before the first until the last has passed. This is inherent to History being the Events that ended before the Replay Point.
- **Expired confirmation times go at every moment** (`count(...).within(...)`), so `retainedValues()` does not depend on which Rule read the count and a replay can match it.

An earlier version of this section made every recorded value depend on the whole moment (the earliest start of the Replay Point at that moment). That chained windows to themselves, so any Rule with a moving average pinned the Replay Point at the first Sample (found by ticket 11). The sums are now exact (see "Moving averages are correctly rounded"), the dependencies are per value, and `ReplayPointBoundsTest` asserts for every construct that the Replay Point stays within a bound of the stop on a long input. `ReplayPointOptimalityTest` searches, for many stops, the latest start that reproduces many different continuations and asserts the Replay Point is at most three moments before it (the run that just ended, the previous Sample).

Preconditions, each with a test:

- `droppedValues()` is 0. Once a window or the confirmation times dropped an entry because of the Retention Limit, which entries are held depends on when entries arrived, and a replay that starts later can hold different ones (`ReplayPointTest.aSmallRetentionLimitThatDroppedEntriesIsAPrecondition`). `droppedValues()` itself, a count since the Detector was built, and the one warning logged at the first drop are never reproduced.
- The replay gets the same input in the same order: all Samples and time advances from the Replay Point on, and `close()`.
- Side effects must be suppressed up to the stop by the application: the replay reports Events that already happened.

The Replay Point is not minimal in general: it keeps before the Event for the one moment in which a run ended, it does not exploit that a replayed Event might happen to end the same way, and a Rule that ended its Event on an End Condition while `when` still holds keeps it back to the Event's start for as long as `when` holds (the replay would have to know that its own Event ends by then).

## Compatibility policy

A Snapshot is readable by any rbed version with the same format version. The format version changes only when the shape of the state changes; a release that changes it says so in its release notes, and rejects older Snapshots with a message pointing to the Replay Point. There is no promise of migrating across format versions: the Replay Point is the way across.

## Alternatives considered

- **Replay only.** Rejected as the only answer: an Event in progress, a window or a `latest(...)` Aggregate reaches back a data-dependent distance, and a restart is slow when the stream is long.
- **Java serialization.** Rejected: it ties the format to class layout and is a known hazard on untrusted input; the explicit format is small and checked.
- **Restoring into different Rules.** Rejected by design: the fingerprint makes a deployment that changed a Rule fall back to a replay instead of continuing from an incompatible state.

## Moving averages are correctly rounded (since 0.4.0)

A moving average used to keep a running compensated sum that also subtracted the values leaving the window, so its last bit depended on the whole history, and a replay (which restarts the sum) could not be guaranteed to match. The sum of a window is now exact: a superaccumulator (`ExactSum`), one fixed-width integer in units of 2^-1074 held in 68 limbs of 32 bits, with exact add and exact remove by integer arithmetic (limbs are not normalised while adding, so they are a function of the multiset of values alone), converted once to the nearest double (ties to even) and then divided by the window size. (A first version used Shewchuk expansions; they were wrong at the overflow edge, history dependent there, and allocated once a huge value had passed.) The average therefore depends only on the multiset of values currently in the window, never on their order or on values that left, which is what lets the Replay Point drop the history before the window. The sum is infinite exactly when IEEE rounding of the true sum overflows (`MAX_VALUE + 2^970 - 1` is `MAX_VALUE`, `MAX_VALUE + 2^970` is infinite). Nothing is allocated, ever. A Snapshot stores the non-zero limbs. The format version stays 1 (unreleased). Consequence: results can differ from 0.3.0 in the last bit where the old compensated sum was off by one ulp. Cost: pushing stays allocation free, also after huge values have passed (`PerformanceTest.movingAveragesDoNotAllocateAfterHugeValues`); throughput of the performance tests, expansions against superaccumulator measured back to back on one machine: a single threshold 30.5 M Samples/s and 29.4, a realistic rule set 3.50 and 2.89, 50 Rules over 20 Channels 0.85 and 0.91 (the first version of this section, with 0.3.0's compensated sum as the base, said 25.6 to 37.0, 3.30 to 3.79 and 0.94 to 0.87 on a quieter machine). The Snapshot of the realistic Rule set is unchanged at about 240 KiB (only non-zero limbs are written).
