# Spec: resuming a stream after a restart

Status: done

## Problem Statement

An application feeds a Detector from a message stream such as a Kafka topic. When it stops (a deployment, a crash) and starts again, it wants to continue at the next message as if it had never stopped: the same Events, at the same timestamps, with the same flags and Aggregates, each reported exactly once.

rbed keeps a Detector's state in memory. History restores Ended Events for `after`, `unless`, `count`, `totalDuration` and `latest(...).duration()`, but nothing else: not an Event in progress (Pending or Confirmed), not a running duration, not the Samples inside a moving-average window, not `rate()`, `age()` or `maxGap`, not a Rule's knowledge that its `when` Condition has stopped holding, not the Aggregates that `latest(...).min/max/mean` read (History Events carry none), and not the Sample index of sampling-rate mode.

The obvious workaround, replaying recent messages into a fresh Detector, is only exact if the replay starts early enough, and the application cannot know how early:

- A Rule whose last Event Ended on its End Condition may still see `when` holding; a fresh Detector would start a new Event (with a Truncated start) at the first replayed Sample, an Event the uninterrupted run never had.
- An Event in progress, a duration, a moving-average window and `latest(...)` Aggregates each reach back a different, data-dependent distance.

There is also no way to save the state itself and continue from it, and no way to learn from a Detector how far back its Rules look, which an operator needs to size the topic's retention. The README and the documentation site say nothing about restarting beyond History.

## Solution

Three complementary capabilities, documented together as one recipe:

1. **Snapshot and restore.** A Detector can write its complete state as a **Snapshot** (a versioned, self-describing byte array) between Samples. A new Detector built with the same Rules and options can be restored from it and continues exactly as the original would have. The application stores the Snapshot with its stream position; after a restart it restores and continues with the next message, without any replay.
2. **Replay Point.** A Detector reports, at any moment, the earliest timestamp from which replaying the same input into a fresh Detector (with History of the Events Ended before that timestamp) reproduces its state. This is the exact fallback when no Snapshot is available (none taken yet, Rules changed, Snapshot lost or of an unsupported format version), and it also bounds the replay of the messages after the latest Snapshot.
3. **Memory Horizon.** A Detector reports how far back its configuration makes it look: the longest time window and the largest Sample count any Rule or watched Expression uses. Operators use it to size the topic's retention and the Snapshot interval; it is a configuration bound, not a guarantee about Events in progress (the Replay Point is).

The README gets a section on resuming a stream with the recipe (what to persist, how to restart, preconditions, Kafka notes), a runnable example test proves it for every possible stop point with an in-memory message log and store, and the documentation site gets a page "Resuming a stream" next to "Restarts: History" that lets the reader move a stop point and compare a naive restart, History only, a restart from the Replay Point and a restore from a Snapshot against the uninterrupted run.

## User Stories

1. As an application developer, I want to stop and restart my application without losing or duplicating Events, so that alerts and records stay correct across deployments.
2. As an application developer, I want to save a Detector's complete state, so that I can continue after a restart without replaying anything.
3. As an application developer, I want to restore a Detector from that state with the same Rules, so that it continues exactly where it stopped.
4. As an application developer, I want a Snapshot to be a plain byte array, so that I can store it anywhere (a database column, a compacted Kafka topic, a file).
5. As an application developer, I want a Snapshot to carry everything: Events in progress, running durations, moving-average windows, the values behind `rate()`, `age()` and `maxGap`, each Rule's knowledge of `when`, `latest(...)` Aggregates, Event counts and durations within windows, and the Sample index of sampling-rate mode, so that a restore is exact in every mode.
6. As an application developer, I want restoring with different Rules or options to be rejected with a clear message, so that a deployment that changed a Rule never continues from an incompatible state.
7. As an application developer, I want restoring a Snapshot of an unsupported format version to be rejected with a clear message, so that I know to fall back to a replay.
8. As an application developer, I want to know which rbed versions can read which Snapshots, so that I can plan upgrades.
9. As an application developer, I want taking a Snapshot inside a listener callback to be rejected, so that I never store a half-processed moment.
10. As an application developer, I want a Snapshot's size to be bounded by the Retention Limit, so that it cannot grow without limit.
11. As an application developer, I want taking a Snapshot to leave the Detector unchanged, so that I can take one at any time between Samples.
12. As an application developer, I want rbed to tell me how far back my stream must be replayed when I have no usable Snapshot, so that I do not have to derive it from my Rules by hand.
13. As an application developer, I want that Replay Point to account for Events in progress, durations, windows, `rate()`, `age()`, `maxGap`, Rules that have not seen `when` stop holding, and `latest(...)` Aggregates, so that a replay from it is exact.
14. As an application developer, I want reading the Replay Point to be cheap enough to store with every commit, so that a replay is always possible.
15. As an application developer, I want to combine both: restore the latest Snapshot and replay only the messages after it, so that I can take Snapshots rarely.
16. As an operator, I want to know the longest time window and the largest Sample count my Rules use, so that I can size the topic's retention and choose a Snapshot interval.
17. As an operator, I want that Memory Horizon to be clearly a configuration bound, so that I do not mistake it for a guarantee about long-running Events.
18. As an application developer, I want a precise list of what to persist (Snapshot or Ended Events and Replay Point, plus the stream position, written atomically or idempotently), so that I can design my storage once.
19. As an application developer, I want Ended Events to have a natural key (Rule name and start), so that writing one twice during a replay is harmless.
20. As an application developer, I want to know how to suppress side effects while replaying, so that nothing is reported twice.
21. As an application developer, I want to know how time advances fit in (recorded like messages, or derived from Sample timestamps), so that a replay reproduces them.
22. As an application developer, I want to know that one Detector per key and ordered processing per key are required, so that Kafka partitioning maps onto Detectors correctly.
23. As an application developer, I want a runnable example of the whole recipe without Kafka or a database, so that I can copy its structure.
24. As a reader of the documentation site, I want to move a stop point and compare a naive restart, History only, a replay from the Replay Point and a restore from a Snapshot against the uninterrupted run, so that I understand what each one preserves.
25. As a reader of the documentation site, I want the Replay Point and the Memory Horizon drawn on the timeline, so that I see how far back each reaches and why.
26. As a coding agent, I want the recipe in the Markdown twin and llms-full.txt, so that I can implement it for a user.
27. As the maintainer, I want the guarantee proven by tests that compare, for every stop point of several representative Rule sets, the resumed run (by Snapshot, by Replay Point, and by both combined) with the uninterrupted run, so that it is real.
28. As the maintainer, I want the Snapshot format and its compatibility policy recorded in an ADR, so that future changes keep old Snapshots readable or reject them deliberately.
29. As the maintainer, I want the new concepts in the glossary, so that the README, the Javadoc and the site use one word for each.
30. As the maintainer, I want the feature released as a new minor version, so that users see a new API appeared.
31. As the maintainer, I want a restored Detector to be indistinguishable from the original in every observable way, for every input, with no exception, so that users can rely on restores blindly.
32. As the maintainer, I want that guarantee tested exhaustively (every moment, chains of restores, thousands of random Rule sets and inputs) and the tests proven to fail when any piece of state is missing, so that "never a difference" is backed by evidence.

## Implementation Decisions

- **The guarantee (non-negotiable).** A Detector restored from a Snapshot is observationally indistinguishable from the Detector the Snapshot was taken from: for every input that follows, every callback (kind, order, and the complete Event: name, start, Confirmed, end, Truncated flags, every Aggregate bit for bit), every value read through `value(...)`, `replayPoint()`, `memoryHorizon()`, `retainedValues()`, `droppedValues()`, the warnings logged, and every exception thrown (type and message) are identical. There are no preconditions beyond the ones `build()` enforces (same Rules and options, supported format version). Any difference, however small, is a bug and blocks the release. The same holds for the Replay Point under its documented preconditions.
- **Glossary (CONTEXT.md), three new terms:**
  - **Snapshot**: the complete state of a Detector between two moments, as a versioned byte array that a Detector built with the same Rules and options can be restored from. Avoid: checkpoint, dump, savepoint.
  - **Replay Point**: the earliest timestamp from which replaying a Detector's input into a fresh Detector, with the Events Ended before it supplied as History, reproduces the Detector's state. Avoid: checkpoint, watermark.
  - **Memory Horizon**: the longest time window and the largest Sample count the Rules and watched Expressions of a Detector use by configuration. Avoid: lookback, retention (Retention Limit is a different concept).
- **Snapshot API:**
  - `Detector.snapshot()` returns a `byte[]` with the complete state at the latest moment processed. It throws `IllegalStateException` when called from within a listener callback, and works after `close()` (the state of a closed Detector, which restores as closed).
  - `Detector.Builder.restore(byte[] snapshot)` makes `build()` produce a Detector in that state instead of a fresh one. `build()` rejects, with `IllegalArgumentException` and a clear message, a Snapshot whose format version is not supported, whose Rule fingerprint differs from the Builder's Rules, or whose options (sampling rate, Retention Limit, watched Expressions) differ. `restore` and `history` together are rejected (a Snapshot already contains what History would add).
  - The listener is not part of the Snapshot; the restored Detector reports to the Builder's listener.
- **Snapshot format:** written with the JDK only (no dependency): a magic header, a format version, a fingerprint, then the state. The **fingerprint** is a hash over a canonical description of every Rule (name, Conditions, durations, End Condition, `maxGap`, aggregated Channels) and of the options; this requires deterministic, readable descriptions of Conditions and Rules, which this spec adds (Expressions already have them since 0.3.0). The state covers everything the Detector holds: Channel tracks and their derived tracks (moving-average windows, rate, age), Pulse Channel state, every Rule's state (Pending/Confirmed Event in progress with its Aggregates, duration progress, End Condition progress, whether `when` has been seen not holding, data-gap state), Event state per Rule (latest Event with Aggregates, count timestamps within windows, total durations), `now`, the last Sample, the Sample index, the closed flag, dropped/retained counters, and the History already remembered. Its size is bounded by the Retention Limit.
- **Compatibility policy (ADR-0007):** a Snapshot is readable by any rbed version with the same format version; the format version changes only when the state's shape changes; an rbed release that changes it says so in its release notes and rejects older Snapshots with a message pointing to the Replay Point. No promise of cross-format migration.
- **Replay Point API:** `Detector.replayPoint()` returns an `OptionalLong`: empty before the first Sample and in sampling-rate mode (a fresh Detector cannot continue a Sample index; use a Snapshot there); otherwise the minimum over: the start of every Event in progress and of its End Condition duration; for every Rule that has not seen its `when` Condition stop holding since its last Event, the last moment it saw it not holding (or the first Sample); the oldest Sample inside any moving-average window; the previous Sample of every Channel read by `rate()`, `age()` or `maxGap`; the start of the latest Event of every Rule read through `latest(...).min/max/mean`, and of every Rule read through `latest(...)` while its Event is in progress. Whatever the implementation finds necessary beyond this list to pass the property tests is part of the decision. Reading it does no work proportional to history and allocates nothing beyond the result.
- **Memory Horizon API:** `Detector.memoryHorizon()` returns a small immutable value with the longest time window in milliseconds (from `forDuration`, End Condition durations, `averageOverDuration`, `within(...)`, `maxGap`, and the like) and the largest Sample count (from `forSamples` and `averageOverSamples`), over all Rules and watched Expressions; it is computed once in `build()`. Its Javadoc says plainly that Events in progress, Rules waiting for `when` to stop holding, and `latest(...)` can reach further back, and points to the Replay Point.
- **ADR-0007** records: why both Snapshot and Replay Point exist (instant restore vs. no format to keep stable), the Snapshot format, fingerprint and compatibility policy, the Replay Point's definition and preconditions, and the Memory Horizon as a configuration bound.
- **README:** a section "Resuming a stream" after "Restarts: History": the three capabilities, what to persist (Snapshot with the stream position; or Ended Events keyed by Rule name and start, the Replay Point with the stream position, the last processed position; atomically or idempotently), the restart procedures (restore and continue; or History of Events Ended before the Replay Point, seek, replay with side effects suppressed up to the last processed position, continue; or both combined), the preconditions, Kafka notes (one Detector per key, ordered per partition, retention ≥ Memory Horizon and back to the oldest stored Replay Point, compacted topic for Snapshots) and a link to the example test. The "Errors and validation" table gains the new rejections.
- **Example test** (in the library's examples, like the domain examples): an in-memory message log with offsets stands in for the topic, an in-memory store for the database, a listener whose side effects go to an output list. For a representative Rule set and every stop offset it shows both recipes (restore from the Snapshot taken at the stop; replay from the stored Replay Point) and the combined one (an older Snapshot plus replay of the tail), each producing exactly the uninterrupted output. Public API only, no dependencies.
- **Documentation site:** a Guide page "Resuming a stream" after "Restarts: History", with a Scenario whose parameters are the stop point and a choice of restart (naive, History only, Replay Point, Snapshot). The bridge result carries the Replay Point and Memory Horizon at the stop and the uninterrupted run's Events for comparison; the chart marks the stop, the Replay Point and the Memory Horizon and shows which Events differ. Built with the site's recipe ("Adding a page"); the Snapshot runs in the browser too (TeaVM), which the parity test covers.
- **Version:** 0.4.0 (after 0.3.0). Releasing follows RELEASING.md.

## Testing Decisions

- **Good tests compare observable output:** the Events (names, start, Confirmed, end, Truncated flags, Aggregates) and listener callbacks of a resumed run against an uninterrupted run, and the documented rejections. They never inspect the Detector's internals or the Snapshot's bytes beyond the header.
- **One seam for the guarantee: the library's public API.** Property-style JUnit tests run, for each of several representative Rule sets and every stop point: (a) snapshot at the stop, restore into a new Detector, continue; (b) replay from the stored Replay Point with History; (c) restore an older Snapshot and replay the tail; each must equal the uninterrupted run. The Rule sets together cover durations (`forDuration`, `forSamples`), End Conditions with `when` still holding at the end, `maxGap` and data gaps, moving averages over Samples and over a duration, `rate()`, `age()` with time advances, `after(...).within(...)`, `count(...).within(...)`, `totalDuration`, `latest(...).duration()` and `latest(...).max(...)`, Pulse Channels, watched Expressions, sampling-rate mode (Snapshot only) and History supplied at the very first build. A replay from one Sample after the Replay Point must differ for at least one stop point per Rule set where it should, so the Replay Point is not trivially "the beginning".
- **Differential testing of the guarantee, as strict as possible:**
  - **Twin runs.** A test harness runs an original Detector and its restored twin side by side and, after every subsequent push, advance and close, compares everything listed under "The guarantee": the full callback sequences, the complete Events (doubles compared bit for bit, not with a tolerance), `value(...)` of every watched Expression, `replayPoint()`, `retainedValues()`, `droppedValues()`, and the exceptions thrown for the same invalid input (e.g. a timestamp that does not increase, a non-finite value, a push after `close()`).
  - **Every moment.** For every Rule set and every moment of its input (every Sample, every advance, after `close()`), a Snapshot is taken there and its twin compared to the end.
  - **Chains of restores.** A run that is snapshotted and restored after every single moment (and runs with restores at random moments) equals the uninterrupted run; a Snapshot of a restored Detector is byte-for-byte identical to the Snapshot it was restored from (the round trip is the identity).
  - **Random Rule sets and data.** A seeded generator (hand-written, no dependency) builds Rule sets from every construct the library offers (all Conditions and Expressions, durations, End Conditions, `maxGap`, Rule references, Pulse Channels, watched Expressions, History, sampling-rate mode, Retention Limits small enough to drop entries) and random inputs (irregular timestamps, gaps, advances, missing and Pulse values, values at and around thresholds, NaN-producing warm-ups). The regular build runs thousands of cases with fixed seeds; an extended profile runs far more with fresh seeds. A failure prints its seed and the shrunk input, so it reproduces as a plain JUnit case, which is then added as a regression test.
  - **The tests must have teeth.** For every piece of state the Snapshot writes, the implementer demonstrates (recorded in the ticket's Comments) that leaving it out, or restoring it slightly wrong, makes at least one test fail. A piece of state whose omission no test notices means the tests are missing a case; add it.
  - **Across runtimes.** A Snapshot written on the JVM restores in the compiled browser module and vice versa, and both continue identically (the site's parity test).
- **Snapshot contract tests:** snapshot inside a callback rejected; restore with a changed Rule, a renamed Rule, a different option, a corrupted or truncated byte array, or another format version rejected with the documented messages; restore together with History rejected; snapshot of a closed Detector restores closed; snapshot leaves the Detector's subsequent Events unchanged; Snapshot size stays bounded under the Retention Limit; the readable descriptions of Conditions and Rules are deterministic.
- **Memory Horizon tests:** expected millis and Sample count for Rule sets mixing every windowed construct and watched Expressions.
- **Performance:** existing allocation checks still pass (taking a Snapshot may allocate; pushing must not allocate more than before); a note on Snapshot time and size for the realistic Rule set of the performance tests.
- **Site:** the existing bridge seam (BridgeTest + parity + SourceTest) for the new Scenario, including a Snapshot round trip in the compiled module; the browser smoke tests cover the page.
- **Prior art:** the domain example tests, `EndConditionTest` (restart rule), `TimeAdvanceTest`, `RetentionTest`, `ExpressionValueTest` (watched Expressions and their readable descriptions), the History tests, `PerformanceTest`; on the site, the History page's Scenario and BridgeTest's restart tests.

## Out of Scope

- A Kafka (or any messaging/database) dependency in the library or its tests.
- Migrating Snapshots across format versions.
- Restoring a Snapshot into a Detector with different Rules (rejected by design).
- Exactly-once delivery machinery: the recipe states the requirements; implementing a transactional outbox is the application's.
- Reading Conditions or Rule states from the Detector beyond what this spec adds.

## Further Notes

- This spec grew from the question "what must I persist to resume a Kafka stream without interruption?" (October 2026). With rbed 0.2/0.3 a replay is the only way, and its start cannot be derived safely by the application: a Rule whose `when` still holds after its Event Ended on an End Condition would create an extra Event in a fresh Detector, and `latest(...)` Aggregates are not carried by History. The maintainer asked for Snapshot/restore and the Memory Horizon in addition to the Replay Point.
- Builds on 0.3.0 (watched Expressions and readable Expression descriptions); it can start once 0.3.0 is released.
- If a property test shows a case the Replay Point cannot make exact with reasonable bookkeeping, record it in ADR-0007 and the Javadoc as a precondition rather than weakening the guarantee silently; the Snapshot has no such limit.
