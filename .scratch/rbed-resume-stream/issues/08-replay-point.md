# 08: Replay Point

**What to build:** `detector.replayPoint()` returns the Replay Point as an `OptionalLong`: empty before the first Sample and in sampling-rate mode, otherwise the earliest timestamp from which replaying the same input into a fresh Detector, with History of the Events Ended before it, reproduces the Detector exactly. It covers every component the spec lists (Events in progress and End Condition durations, Rules that have not seen `when` stop holding, moving-average windows, the previous Sample behind `rate()`, `age()` and `maxGap`, `latest(...)` Aggregates and running Events) plus whatever the tests show is needed. Reading it does no work proportional to history and allocates nothing beyond the result. See spec: Implementation Decisions "Replay Point API", "The guarantee"; Testing Decisions.

**Status:** done

## Comments

- API: `Detector.replayPoint()` (`OptionalLong`; empty before the first Sample and with a sampling rate). Javadoc has the definition, what to replay and the preconditions; ADR-0007 has a section "The Replay Point".
- Mechanism (what ticket 09/10/11 and the site can rely on): `Detector.settle(timestamp)` runs once per moment after the Channel tracks are updated and before the Rules are evaluated. It computes `closedNow`: the latest timestamp from which a replay reproduces how the Rules evaluate this moment (this moment, lowered by the need of every track, the latest Event Aggregates that are read, and the runs of Rules that are busy). Everything recorded at the moment uses it: a track's `lastNeed`/`previousNeed` (`ValueTrack`), a window entry's `needs[]` and `expiredNeed` (`Window`), a Rule's `runStart`, `falseSeen`, `latestEndedStart` (`RuleState`), `lastSampleClosed` (`Detector`). `replayPoint()` is the minimum of these and `closedNow`. All of it is in the Snapshot (`save`/`load`), so a restored Detector reports the same Replay Point; the twin harness compares `replayPoint` as an observable.
- Beyond the spec's list, the tests showed these were needed: the state a decision read (an Event that started on `rate()` needs the previous value; `when` seen false needs what it was evaluated from), that no Event is split by the point (an Event partly before it would be neither History nor produced again), the Rule's busy span after an Event ended on its End Condition, and expired `count(...).within(...)` confirmation times being dropped at every moment (library change: `retainedValues()` no longer depends on which Rule read the count; found by the extended run, regression test `expiredConfirmationTimesDoNotDependOnWhoReadTheCount`).
- Test harness: `ReplayHarness` (test sources) runs the uninterrupted input once, then for every stop builds a Detector with the History of the Events Ended before the Replay Point, feeds it the input from the Replay Point to the stop (output dropped) and compares everything observable from the stop on (not `droppedValues` and `replayPoint`, which the replay cannot reproduce). `ReplayPointTest`: ten representative Rule sets (end condition with `when` still holding, durations and Sample counts, `maxGap` with gaps, moving averages with `rate()`/`age()`, nested moving averages, Events across Rules, `latest(...)` Aggregates, Pulse Channels with `age()` and with `maxGap`, History at the first build) x 12 inputs of 60 moments, and 3000 generated cases (about 105,000 stops, 82,000 checked; 5,500 skipped for dropped entries; the Replay Point is before the latest moment in 75,000). Run more with `mvn test -Pdifferential -Dtest=ReplayPointTest#generatedCases -Drbed.diff.cases=40000` (40,000 fresh-seed cases, 1.1 million stops checked: 0 differences after the fixes above); reproduce with `-Drbed.diff.seed=S`.
- Not trivially early: replaying from the next Sample after the Replay Point differs at 18,000 of the 82,000 stops of the generated cases and at least once in every representative set (asserted per set).
- Teeth: each of these changes, made alone, makes `ReplayPointTest` fail (script, one at a time): leaving out the false-moment, the latest-Event start, the previous-value need, the absent-Pulse `age()` need, the Sample window, the duration window's warm-up entry or its entries, the previous Sample behind `maxGap`, the latest moment itself, the busy runs, the settling of window entries or tracks, evaluating a decision at its own moment instead of the closed one, the immediate drop of expired confirmation times, and the gap exception for runs. Two apparent survivors were redundant code (deleted) or missing cases (added tests: nested averages, Pulse with `maxGap`, the expired-count regression, the gap unit test).
- Precondition recorded in ADR-0007 and the Javadoc, with a test: once the Retention Limit dropped entries, a replay can differ (`aSmallRetentionLimitThatDroppedEntriesIsAPrecondition`); `droppedValues()` and the drop warning are never reproduced. The last bit of a moving average is a theoretical precondition (see ADR), never observed.
- Cost: pushing allocates nothing more (PerformanceTest allocation checks pass, 0 bytes/Sample). Per moment, one loop over Channels, Rules and counted Events; windows keep one more `long` per entry (`needs`).
- Reworked after the code review (FIX-A, A3-A5, see `rs-fix-plan.md`): the mechanism above (`settle`, `closedNow`, the whole moment's earliest start for every recorded value) chained windows to themselves and pinned the Replay Point at the first Sample for any Rule with a moving average. It is replaced by per-value dependencies and (start, end] pairs for runs that are over; moving-average sums are exact, so the "last bit" precondition is gone. ADR-0007, section "The Replay Point", is current; `ReplayPointBoundsTest` and `ReplayPointOptimalityTest` check that the Replay Point keeps up with the stop.
